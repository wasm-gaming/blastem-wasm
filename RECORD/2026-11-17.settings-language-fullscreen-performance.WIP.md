## The common part (all the engines with a settings screen)

- **engine-specs `^0.3.2` → `^0.6.0`**. The app imports the helpers from `../engine-specs.js`, the
  runtime copy the Makefile already ships beside the SDK.
- **English and Spanish**:
  - every string of the app (today Spanish, inline) moves into one `{ en, es }` table;
  - the table is read through `host.locale ?? resolveLocale()`;
  - SDK errors stay English and are shown as a detail under the app's own words.
- **Pause menu**: Continuar, the engine's entries, **Ajustes**, **Pantalla completa**, Volver al
  lanzador (UX.md rule 4).
- **Ajustes**: `createSettingsScreen()`.
  - Rows come from `settingsModel()` over the SDK's `config()` / `options()` descriptors (only those
    with a `label`), plus `SHARED_SETTINGS`.
  - A live change is applied at once.
  - A non-live one is saved and passed at the next start; its row says "Se aplica al reiniciar".
  - Choices are saved per engine with `saveSettings('blastem')` and read at mount with
    `loadSettings()`.
- **Fullscreen**: `createFullscreenToggle(root)` (Cmd+Enter / Alt+Enter, Select + Y), plus the
  pause-menu entry.
- **Performance**:
  - `createWakeLock()`, held while playing when "Mantener la pantalla encendida" is on (default
    on);
  - `createPerfCounter()` when "Mostrar rendimiento" is on: fed once per emulated frame where the
    SDK reports frames, else counting display frames.
- **Controls and audio pacing**: per engine, below.
- **Checks**:
  - `make test` / build;
  - in Chromium, with the owner's test ROMs where needed: the pause menu, every setting applied (or
    noted as on restart), saved across a reload, fullscreen by key and by menu, the counter, en / es;
  - a phone width.
- **Release**: minor.

## Walkthrough (2026-11-17 22:30 UTC) — BlastEm done

Adds: what was built, what was settled from the plan's "to check" items, and the checks. It is
mGBA's template (mGBA-wasm, same record), adapted.

**Settled**:
- **The bump crosses 0.4 and 0.5 without changes**: the SDK type-checks and its 14 tests pass on
  engine-specs 0.6.
- **Controls: yes, keys and pads, live**, not on restart. BlastEm's bindings are compiled into the
  WASM (its `default.cfg`), and writing a user config blind risked the rest of its settings. So
  the bindings sit in front of SDL instead (`src/blastem.controls.ts`):
  - **keys**: a physical key bound to a control is swallowed at the window (capture phase, real
    presses only) and replayed on the canvas as BlastEm's default key for that control, with
    `code`, `key` and `keyCode`. A default key no control has any more is swallowed.
  - **pads**: while the game runs, `navigator.getGamepads()` is wrapped, and each pad's buttons
    are reordered so the chosen button sits where BlastEm's default looks for it. It is restored on
    close.
  - Player 1's keys (player 2 has none in BlastEm's defaults); the button table applies to every
    pad.

**SDK** (`src/`):
- `blastem.controls.ts`: `BLASTEM_CONTROLS` (A B C X Y Z Mode Start and the d-pad, with BlastEm's
  default keys and buttons), `controlTables()`, `remapPad()`.
- `blastem.sdk.ts`: `play.setControls()`, the key listener and the `getGamepads` wrapper.
- `blastem.options.ts`:
  - `renderFilter` → Vídeo "Suavizado" (Píxeles nítidos / Suavizado), live;
  - `region` → Emulación "Región", applied on restart.

**App**: derived from mGBA's finished app, with these differences:
- BlastEm's settings are `config()` (smoothing, region), and each change is written to the
  payload it belongs to;
- the counter counts display frames (BlastEm's loop runs inside the WASM).

**Checks**:
- `tsc` clean; `make test` 14 / 14.
- In Chromium, with the published WASM and a homebrew Mega Drive ROM (BlastEm runs and draws with
  WebGL):
  - Ajustes: Vídeo / Emulación / Controles, en and es;
  - → on Suavizado changes the canvas;
  - the counter at 60 fps; Alt+Enter enters fullscreen;
  - A takes K, then B takes K and A gets S (swap);
  - after a reload the choices are back; 390px.
- Remapping reaching SDL:
  - after A → K, pressing K reaches the page as a replayed `KeyA`, and the real `KeyA` is
    swallowed;
  - with a fake pad, binding B to button 3 through the screen makes `getGamepads()` report
    button 1 (B's default) when 3 is held, and button 3 (Y's) when 1 is held (the swap).
